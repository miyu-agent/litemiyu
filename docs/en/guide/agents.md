# Subagents, cross-session messages and loops

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page covers three features: having the AI do several things at once, having the AIs in several windows cooperate, and having the AI repeat a task on its own. All three are available only in sessions with all features.

## Background commands

Some commands run for a long time, such as starting a development server or running a full test suite. The AI can put such a command in the background and carry on with other work; it is notified automatically when the command ends.

While background commands are running, the middle of the footer shows `Background: 1`. Click it, or press `↓` and then `Enter` with an empty input box, to open the background panel:

```text
╭─ Background · 1 running ───────────────────────────────────────╮
│                                                                │
│❯ sleep 30; echo done                             (running 2s)  │
│                                                                │
╰─ j/k select · Enter expand · x stop · Esc close ───────────────╯
```

`Enter` expands the output and `x` stops the selected command.

By default a background command may run for at most 30 minutes; after that it is stopped and the AI is told. Change the limit under `Longest background command` on the `General` page of `/config`; the maximum is 2 hours.

> Background commands belong to the window. When you close the LiteMiyu window, any that are still running stop too. With shell integration they belong to the terminal; see [Using LiteMiyu in your shell](shell.md#background-commands-loops-and-reports).

## Subagents

A subagent is a sub-session the AI starts. The AI hands it a fairly self-contained task, the subagent works on it in the background, and it reports the result back. This keeps the main session's context from filling up with intermediate content, and lets several things proceed at once.

You do not need to do anything special; just tell the AI. For example:

```text
Start two subagents: one finds functions in src/ without tests, the other finds outdated commands in the README. Then give me a summary
```

Once subagents are working, rows appear below the input box:

```text
 ● Main session
 ○ Subtask  Replying                                        4s
```

- There is one row per subagent, showing its name, what it is doing (`Thinking`, `Replying`, `Done`) and the elapsed time.
- With an empty input box, press `↓` to move focus to the rows, select a subagent and press `Enter`: the conversation switches to that subagent's, and the top right of the input box shows `Subagent · <name>`. Select `Main session` and press `Enter` to switch back.
- When a subagent finishes, the main session shows a line `● Background task done · <name> · <time>` and the AI goes on to handle its report.

A few things to know:

- A plain subagent sees only the task description the AI gave it, not the main session's conversation. To carry on from the conversation so far, use a fork subagent, described below.
- Subagents use the same model as the main session, and their cost is included in the main session's cost.
- A subagent cannot ask you questions. Confirmations for dangerous commands still come to you, and their title says which subagent is asking.
- `/stop` stops running subagents as well.
- When you delete the main session with `/delete`, the sessions of the subagents it started are deleted too.

### Reopening a subagent's session

A subagent's session does not appear in `/sessions` or under `Recent sessions` in the sidebar, but you can open it directly with its full session ID and go on talking to it:

```bash
litemiyu -s <subagent session ID>
litemiyu ask -s <subagent session ID> "Check it once more"
```

- To find the ID: while the subagent is still shown in the rows below the input box, switch into it and run `/status`; `Session ID` there is its ID. You can also copy it by clicking the short ID in the sidebar. Once a subagent has finished and left those rows, nothing in the interface shows its ID, so note it down beforehand if you will need it.
- What opens is the subagent's own conversation. A plain subagent's conversation starts from the task the AI gave it; when you talk to a fork subagent, the model still sees the conversation from before the fork.
- What you say there and what it answers are not reported to the main session, and the cost is not included in the main session's cost.
- While the session that started it is open in another window, the subagent's session cannot be opened, and LiteMiyu says `session … belongs to a subagent, and session … that started it is open in another window`. Close that window first.
- While a subagent's session is open this way, messages the AI in the main session sends to it are not delivered, and the AI gets a failure result. The main session that started it cannot be deleted either; you are told the session is open in another window.
- `-c` opens the latest main session only, never a subagent's session.

### Subagents that continue the conversation (fork)

Sometimes a task needs what was said earlier. For example, you and the AI have just agreed on a plan and you want a subagent to carry out one part of it. A plain subagent does not fit well here: it cannot see your discussion, so the AI has to write the whole plan out again for it. In this case the AI can start a "fork subagent" instead. A fork subagent continues from a copy of the main session's conversation as it is at this moment, sees everything said so far, and uses the same model as the main session.

You can simply say:

```text
Fork a subagent to change src/parser.rs following the plan we just agreed on, then tell me what it changed
```

The AI may also decide on its own when to fork. In the subagent rows, a fork subagent has a fork mark before its name:

```text
 ● Main session
 ○ ⑂ Change parser  Replying                                6s
```

- When you switch into a fork subagent, its conversation starts from its own part: the first message is the task the AI gave it, preceded by a short note in English that tells it it is a fork. The conversation before the fork stays in the main session and is not shown again in its conversation.
- After the fork, each side goes its own way. What is said in the main session afterwards is not visible to the fork subagent, and what the fork subagent does along the way is not visible to the main session, which receives only its final report.
- Compacting (`/compact`) or undoing (`/undo`) in the main session later does not affect a fork subagent that has already started: it keeps the conversation as it was at the fork.
- A fork subagent's record keeps only its own part; the part before the fork is read from the main session's record each time, so it does not take extra disk space. For the same reason, a fork subagent cannot be opened once the main session's record is gone.
- A fork subagent cannot fork again, but it can start plain subagents.

> Recommended: use a plain subagent when the task has little to do with the earlier conversation. It starts from a clean task description and uses less context. Use a fork when the work has to carry on from the earlier discussion.

## Cross-session messages

You can have several LiteMiyu windows open at once, one session each, working on different projects or tasks. The AIs in those sessions can send each other messages:

- The AI sees your other sessions with the `sessions` tool and sends a message to one of them with `send_message`.
- If the receiving session is open, its AI reads the message at its next step; if it is idle, it starts a new turn with the message. The conversation shows `Message from session <id> "<title>"`.
- If the receiving session is not open, the message waits until that session is next opened. LiteMiyu has no background process and does no work on behalf of closed sessions.
- The AI can also ask to be told when the other side goes idle: when the other session's turn ends, this one receives a notice.

For example, with the backend in one window and the frontend in another, you could say:

```text
When the API change is done, message the frontend session with the new field names
```

> Give your sessions titles that make sense (`/rename`); the AI finds the right one much more reliably.

## Loops (/loop)

`/loop` has the AI do the same thing repeatedly. It suits anything you have to wait for, such as CI finishing, or checking a log every so often.

### Fixed interval

```text
/loop 5m check whether CI has finished; if it failed, read the log and fix it
```

The AI runs it once right away and then sends the same prompt every 5 minutes. Write the interval as a number and a unit, such as `5m` or `2h`.

### Letting the AI set the pace

```text
/loop keep an eye on CI and tell me the result when it finishes
```

Without an interval, the AI decides after each run when to come back (at least 1 minute later). If it considers the job done and schedules no further run, the loop simply ends.

The `/loop` line you typed is shown in the conversation exactly as you typed it, the same way as your other messages, and the AI runs it right away.

### No prompt

```text
/loop
```

With `/loop` alone and nothing after it, the AI decides both what to do and when to come back, based on what is already in this session. You see `Loop started: the AI decides what to do and when to run next`. As with the previous form, the loop ends when the AI schedules no further run, and the time above the input box disappears.

Each later run adds one dim line to the conversation with the words the loop handed to the AI, for example `Loop · check the time`. A long line is cut short; click it to read the whole text. A loop started without a prompt shows `Loop · decided by the AI`.

### Viewing and stopping

While a loop is running, the time of the next run is shown above the input box on the right.

### Loops and undo

- If you run `/loop` right after an `/undo` that could still be brought back with `/restore`, it counts as you saying something new: the loop runs its first time right away, and the undone turn can no longer be restored. `/restore` then says `Nothing to restore`.
- If a loop is already running and you `/undo` a turn before its next run is due, that run is held back: nothing is sent and nothing is written to the conversation, and the right side above the input box says `Loop waiting on undo`. Once you say something and that turn finishes, or once you run `/restore`, the loop makes up that run, only once however many times it came due meanwhile, and then carries on at its usual pace. A scheduled continuation behaves the same way.

Run `/loop off` to stop it; you see `Stopped this session's loops and scheduled continuations.`. `/loop clear` and `/loop stop` do the same. `/stop` stops the loop and any scheduled continuation along with the current turn.

> Loops only run while the window is open. Closing the window stops the loop, and the next time you open the session it says `Loops and scheduled continuations stopped when the window was closed. Run /loop to start a loop again`. For scheduled tasks that keep running with the window closed, use [Miyu](https://github.com/miyu-agent/miyu).

## Scheduled continuation

Without running `/loop`, the AI can also set a time for this session and carry on by itself when that time comes. For example, when you ask it to "check in 10 minutes whether CI has finished", it calls the `schedule_wakeup` tool and the timeline gets one more step:

```text
Schedule · CI takes about ten minutes · in 10m (2026-11-20 14:22)
```

The time is then shown above the input box on the right, the same way a loop is shown. When the time comes, the prompt the AI set is handed to this session and the AI runs one more turn. A scheduled continuation runs once: if the AI schedules another one during that turn, it runs once more; if it does not, that is the end.

- The delay is at least 1 minute.
- A session has one scheduled continuation at a time; when the AI schedules again, the new one replaces the old one.
- If the AI is in the middle of a turn when the time comes, the prompt is queued and handed to the AI at the next step of that turn, without interrupting what it is doing.
- Pressing `Esc` to interrupt the current reply does not cancel the scheduled continuation. To cancel it, run `/loop off` or `/stop`, or ask the AI to cancel it.
- Subagents and `litemiyu ask` cannot schedule a continuation, because they end as soon as they have answered.

> Like loops, a scheduled continuation only works while the window is open, because LiteMiyu has no process that stays in the background. Closing the window cancels it and it will not run (switching to another session in this window does not: the session stays in the background); the next time you open the session it says `Loops and scheduled continuations stopped when the window was closed. Run /loop to start a loop again`. If you still need it, ask the AI to schedule it again.
