# Command line

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This page covers everything the `litemiyu` program does on the command line: starting the full-screen interface, and calling it from scripts and pipes with `ask`.

LiteMiyu's command line is small. There are four things:

| Command | What it does |
|---|---|
| `litemiyu` | Opens the full-screen interface |
| `litemiyu ask` | Sends a message and prints the reply without going full-screen |
| `litemiyu config` | Opens the settings screen |
| `litemiyu help [<command>]` | Prints help |

Providers, models, skills, MCP and sessions are all managed inside the full-screen interface. There are no subcommands for them, and no shell completion.

## litemiyu

Without a command, opens the full-screen interface.

| Option | What it does |
|---|---|
| `-c`, `--continue` | Open the latest session |
| `-s`, `--session <id>` | Open the given session; the full ID is required |
| `--preset <preset>` | The first session uses the given preset; the default preset does not change, see [Presets](presets.md). Cannot be combined with `-c` or `-s` |
| `--bare` | The first session uses the `No features` preset: no tools and nothing added to the conversation. Same as `--preset bare` |
| `--rescue` | Rescue mode; see [Rescue mode](rescue.md) |
| `--base-url <url>`, `--model <name>`, `--api <api>` | The rescue provider; only used with `--rescue` |
| `-V`, `--version` | Print the version |
| `-h`, `--help` | Print help |

For example:

```bash
litemiyu                # a new session
litemiyu -c             # carry on with the last session
litemiyu --bare         # just chat with the model
litemiyu --preset cmd   # the first session uses the preset named cmd
```

When the session does not exist or is open in another window, the program exits right away and says why, for example `litemiyu: session … is open in another window`.

## litemiyu ask

`ask` sends one message, waits for the AI to finish the whole turn (it may call tools and take many steps), prints the reply and exits. It is meant for scripts, pipes and other programs.

```bash
litemiyu ask "What does this project do"
```

`ask` shares its configuration and sessions with the full-screen interface. Without `-c` or `-s` it creates a new session each time, and those sessions also show up under `/sessions` in the full-screen interface.

### Where the message comes from

- From the command line: `litemiyu ask "explain this error"`. Several words are joined with spaces.
- From standard input: with no message, and standard input connected to a pipe or file, everything read is the message.

    ```bash
    echo "Describe Rust in one sentence" | litemiyu ask
    ```

- Both: put a lone `-` in the message, and standard input is appended to what you wrote.

    ```bash
    git diff | litemiyu ask "Review these changes" -
    cat error.log | litemiyu ask "Why did this fail" -
    ```

> With a message and no `-`, `ask` does not read standard input. With no message and a terminal on standard input, `ask` does not wait for you to type; it prints `missing arguments` and exits.

### Options

| Option | What it does |
|---|---|
| `-c`, `--continue` | Continue the latest session |
| `-s`, `--session <id>` | Continue the given session. If the session is open in a window, see [Talking to a running session](#talking-to-a-running-session) |
| `-C`, `--cd <dir>` | Work in the given directory (new sessions only) |
| `--format <text\|json\|jsonl>` | Output format; the default is `text` |
| `--file <file>` | Append this file's path to the message; repeatable |
| `--model <name>` | Use this model, written as `provider/model`; a continued session keeps it |
| `--preset <preset>` | Use the given preset (new sessions only) |
| `--bare` | Use the `No features` preset, no tools; same as `--preset bare` (new sessions only) |
| `--yes` | Allow dangerous commands that need confirmation |
| `--timeout <time>` | Maximum time to wait, for example `30s`, `10m`, `1h` |
| `--max-steps <n>` | Maximum number of model requests |
| `--rescue`, `--base-url`, `--api` | Rescue mode; see [Rescue mode](rescue.md) |

`--file` only writes the file's absolute path into the message; the AI reads the file with its tools. The file's content is not put into the message.

### Output: terminal versus pipe

`ask` splits its output into two streams:

- **Standard output**: only the AI's reply.
- **Standard error**: the steps, that is, everything the AI does, the usage, and the final notes and errors.

So when you run it directly in a terminal, you see the whole process:

```console
$ litemiyu ask "run echo hi and tell me the output"
$ echo hi
hi


The output is hi.
· input 4,001 · cache hit 1,830 (46%) · output 38
```

When standard output goes to a pipe or a file, only the reply arrives there; the steps still appear on the terminal and do not get mixed in:

```bash
litemiyu ask "What does this project do" > answer.md      # the file holds only the reply
litemiyu ask "Suggest a title for this change" 2>/dev/null  # only the reply, no steps
```

Two more differences:

- When standard error is a terminal, the steps are shown in gray; with the `NO_COLOR` environment variable set, they are not colored. Standard output is never colored.
- Terminal control sequences in text written to a terminal are removed first, so that content the model has read cannot manipulate your terminal. Output to pipes and files is left as it is.

`ask` never goes full-screen and never stops to ask you anything, even when it runs in a terminal.

### The three formats

`--format text` (the default) is what you saw above.

`--format json` prints one line of JSON to standard output when everything is finished:

```console
$ litemiyu ask --format json "hello"
{"exit":0,"session":"01a1f772-8d8c-7552-93a0-52bc0e629f9f","turns":[{"reason":"completed","text":"OK, got it.","usage":{"cache_read":0,"cache_write":0,"input":1960,"output":5}}]}
```

Use `jq` to take out the reply:

```bash
litemiyu ask -c --format json "How do I run the tests" | jq -r '.turns[-1].text'
```

`--format jsonl` prints as it goes, one event per line; the last line is always `done`:

```console
$ litemiyu ask --format jsonl "run echo hi and tell me the output"
{"new":true,"session":"01a1f772-8ede-705a-8fbc-c7d3341eef0d","type":"session"}
{"turn":3,"type":"turn.started"}
{"id":"call_8_1","title":"Run echo hi","tool":"shell","type":"step"}
{"id":"call_8_1","ok":true,"summary":"1 line of output","type":"step.done"}
{"text":"The ou","type":"text"}
{"text":"tput i","type":"text"}
{"text":"s hi.","type":"text"}
{"reason":"completed","text":"The output is hi.","turn":3,"type":"turn.ended","usage":{"cache_read":1830,"cache_write":0,"input":4001,"output":38}}
{"exit":0,"session":"01a1f772-8ede-705a-8fbc-c7d3341eef0d","type":"done"}
```

| `type` | Meaning |
|---|---|
| `session` | Which session is used; `new` says whether it was just created |
| `turn.started` | A turn begins |
| `step`, `step.done` | One step of the AI (a tool call) begins and ends |
| `text` | A piece of the reply; the reply arrives in pieces, so there may be many of these lines |
| `turn.ended` | A turn ends, with the reason and the usage |
| `done` | Everything is finished; `exit` is the exit status |

> The examples above were run against a test model with fixed replies. In real use, the reply and the token counts depend on your model.

### Exit status

| Status | Meaning |
|---|---|
| 0 | The turn ended normally |
| 1 | An error occurred, for example a model error, no such session, the window that has the session did not pick up the message, or the configuration file cannot be read |
| 2 | Bad arguments |
| 3 | Interrupted (`Ctrl+C`), or `--timeout` or `--max-steps` was reached |
| 4 | The turn ended, but some steps needed confirmation and were skipped |
| 5 | No usable model |

In a script you can check it like this:

```bash
if ! litemiyu ask --timeout 10m "Run the tests and fix any failures" > report.md; then
    echo "did not end normally, exit status $?" >&2
fi
```

### Dangerous commands and --yes

Nobody can answer a confirmation while `ask` runs. So:

- Dangerous commands that need confirmation (for example `git push --force`) are refused, and the AI carries on with other things. At the end, `ask` reports how many steps were skipped and exits with status 4:

    ```console
    $ litemiyu ask "force-push my changes to the remote"
    $ git push --force origin main · not run: Needs confirmation, no one to confirm

    Finished.
    · input 4,023 · cache hit 1,850 (46%) · output 34
    litemiyu: warning: 1 step needed confirmation and was skipped
    hint: add --yes to allow risky commands that need confirmation in this run
    ```

- With `--yes`, every command in this run that needs confirmation is executed directly. Use it only when you know what the AI is going to do.
- Always-blocked actions such as deleting the root directory are refused even with `--yes`. That does not count as "needing confirmation", so the exit status is still 0.

Which commands fall into each group is described in [Tools and permissions](tools.md).

### Background commands and subagents

If the AI started subagents or background commands during the turn, `ask` waits until all of them have reported and the AI has given its final reply before exiting. While it waits, standard error shows `· Waiting for 1 subagent to report… (Ctrl+C stops waiting)`.

### Talking to a running session

When the session named by `-s` or `-c` is open in a full-screen window, `ask` does not fail and does not open a second copy. It hands the message to that window, waits for the AI there to finish answering, and prints the answer. Other programs can use this to talk to a session you are watching.

```bash
litemiyu ask -s 0199a2b3-0000-7000-8000-000000000001 "The tests finished; the results are in out.log"
```

In that window the message appears just like one you typed into the input box, and the answer is visible on both sides. If the session is idle, the message starts a new turn; if the session is busy, the message joins the turn in progress, the same as typing in the window mid-turn.

A few things differ from an ordinary `ask` in this case:

| Aspect | Behavior |
|---|---|
| Pace of the output | The answer arrives piece by piece (each piece once the AI has finished it), not character by character. All three output formats work |
| `Ctrl+C`, `--timeout` | They only stop the waiting. A message already handed to the window is still processed by the session there |
| Dangerous commands that need confirmation | They are confirmed by the person at that window; `ask` cannot confirm them, and `--yes` has no effect |
| `--model`, `--max-steps` | They have no effect; the session keeps the window's settings |

If you pass an option that has no effect, `ask` only prints a notice on standard error; it does not exit with an error.

If the window does not pick up the message within 45 seconds (for example because it is stuck), `ask` withdraws the message and exits with status 1. The message will not show up in that session later.

Subagent sessions cannot be used this way: while the session that started a subagent is open, `ask -s <the subagent's session ID>` still reports that the session is open in another window.

### Common errors

| Output | Cause |
|---|---|
| `litemiyu: no usable model: none is set up` | No model has been set up yet. Run `litemiyu config` to add one |
| `litemiyu: no session …` | The ID after `-s` is wrong. The full ID is required |
| `litemiyu: session … is open in another window` | The ID after `-s` is a subagent's session, and that session or the one that started it is open in a window; see [Reopening a subagent's session](agents.md#reopening-a-subagents-session). A main session that is open in a window does not produce this; see [Talking to a running session](#talking-to-a-running-session) |
| `litemiyu: the window that has session … did not pick up the message within 45 seconds; not sent` | The window that has this session is not responding, for example because it is stuck. The message has been withdrawn |
| `litemiyu: invalid value 'xml' for '--format'` | The option's value is wrong; the hint on the next line lists the values you can use |
| `litemiyu: time is up` | The `--timeout` was reached |
| `litemiyu: the request limit was reached` | The `--max-steps` count was reached |

## litemiyu config

Opens the settings screen directly; leaving the settings screen also exits the program. It is the same screen as `/config` in the full-screen interface; see [Configuration](config.md).

## litemiyu help

```bash
litemiyu help           # same as litemiyu --help
litemiyu help ask       # help for ask, same as litemiyu ask --help
litemiyu help config
```

## Environment variables

| Variable | What it does |
|---|---|
| `LITEMIYU_HOME` | Puts configuration, data, cache and state all under this directory; see [Where your data lives](data.md) |
| `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME` | Change the location of each of the four kinds of files |
| `LITEMIYU_CATALOG_UPDATE` | Set to `false` to never download the model catalog |
| `LITEMIYU_RESCUE_BASE_URL`, `LITEMIYU_RESCUE_MODEL`, `LITEMIYU_RESCUE_API`, `LITEMIYU_RESCUE_API_KEY` | The rescue provider; see [Rescue mode](rescue.md) |
| `VISUAL`, `EDITOR` | The editor used by `Ctrl+G` and for editing the prompt |
| `NO_COLOR` | When set, the steps printed by `ask` are not colored |
| `LC_ALL`, `LC_MESSAGES`, `LANG` | With the interface language set to `Follow the system`, these decide between Chinese and English |
